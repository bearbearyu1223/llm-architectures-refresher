DEMO 02: The KV cache, and why decode is memory-bandwidth-bound
==========================================================================
device        : mps (Apple arm64)
torch         : 2.13.0
platform      : Darwin 24.6.0 (arm64)
device memory : 17.2 GB

--------------------------------------------------------------------------
0. Why caching is valid at all
--------------------------------------------------------------------------
  Run the model on 4 tokens, then on those same 4 plus 2 more,
  and compare what each run stored for the first 4 positions.

                         shape                                       meaning
  ----------------------------------------------------------------------------
  cache.k    (2, 1, 4, 64, 32)  layers, batch, kv_heads, positions, head_dim
  the slice   (2, 1, 4, 4, 32)          same, but only the first 4 positions

  numbers being compared             1,024

  Subtract one from the other, take absolute values, keep the largest.
  If nothing moved, that largest value is 0:

  max |K_short - K_long|             0.0000
  max |V_short - V_long|             0.0000

  0.0000 is a rounded display, so check exact equality too — this is
  stronger, and rules out a tiny non-zero difference hiding in it:

  torch.equal(K_short, K_long)       yes

  Not close — identical, across all 1,024 numbers. Appending tokens
  cannot reach backwards, so a token's K and V stay valid forever.

  What the cache holds, per layer, for a 4-token prefix:

  tensor  cached?                                                   why
  -----------------------------------------------------------------------
  K           yes                   every later query scores against it
  V           yes                         every later query averages it
  Q            no  position i's query is used at step i and never again

  >> K and V are reused by every future token, and never change once written — so they are worth storing. Q is used once and discarded, which is why it is a KV cache and not a QKV cache.

--------------------------------------------------------------------------
1. The cache changes nothing about the output
--------------------------------------------------------------------------
  generated shape                    (2, 40)
  token ids identical                yes
  first 8 new tokens (cached)        [228, 432, 131, 158, 24, 111, 281, 506]
  first 8 new tokens (uncached)      [228, 432, 131, 158, 24, 111, 281, 506]

  >> The cache is a memoization of keys and values already computed. It is exact — if your cached and uncached outputs differ, you have a bug.

--------------------------------------------------------------------------
2. Without a cache, generation is quadratic
--------------------------------------------------------------------------
  prompt: 64 tokens; model: 7.8M params

  tokens generated  cached (ms)  uncached (ms)  speedup
  -------------------------------------------------------
  64                    54.8871       103.8737    1.89x
  128                   94.5282       234.0838    2.48x
  256                  171.5285       620.7546    3.62x
  512                  306.6524      1956.7814    6.38x

  8x more tokens costs (cached)      5.6x
  8x more tokens costs (uncached)    18.8x
  tokens processed at n=512 (cached) 576
  tokens processed at n=512 (uncached) 163584
  wasted work multiplier             284x

  >> Cached generation scales roughly linearly in tokens. Uncached scales quadratically, because every step redoes the whole prefix.

--------------------------------------------------------------------------
3. How big the cache actually gets
--------------------------------------------------------------------------
  What one token costs, in Llama-3-8B (fp16):

  what                      count   running total
  -------------------------------------------------
  one key vector      128 numbers             128
  + one value vector  128 numbers             256
  x 8 KV heads                              2,048
  x 32 layers                      65,536 numbers
  x 2 bytes (fp16)                        128 KiB

  so one token of context costs      128 KiB
  Every token you have read or written keeps that, for as long as the
  conversation lives. Multiply by context length and by batch:

  context         x KiB/token  cache (batch 1)
  ----------------------------------------------
  8,192 tokens        128 KiB         1.00 GiB
  32,768 tokens       128 KiB         4.00 GiB
  131,072 tokens      128 KiB        16.00 GiB

  Which is the whole formula, just written out in order:

  KV bytes = 2 (K and V) x layers x kv_heads x head_dim x seq x batch x dtype

  Llama-3-8B shapes, fp16, batch 1 — weights are 15.0 GiB:

  variant           kv heads    4k ctx    8k ctx    32k ctx   128k ctx
  ----------------------------------------------------------------------
  as MHA                  32  2.00 GiB  4.00 GiB  16.00 GiB  64.00 GiB
  Llama-3-8B (GQA)         8  0.50 GiB  1.00 GiB   4.00 GiB  16.00 GiB
  as MQA                   1  0.06 GiB  0.12 GiB   0.50 GiB   2.00 GiB

  So does caching cost memory? Yes — at 128k context:

  approach             K/V memory held                           for how long
  -----------------------------------------------------------------------------
  with a cache               16.00 GiB  all 32 layers, the whole conversation
  without a cache             0.50 GiB  one layer, freed as the pass moves on
    + its activations         1.00 GiB                         also transient

  memory held, cached vs not         10.7x more

  And what that memory buys. A request costs roughly in proportion to
  how many tokens the model pushes through itself:

  prompt  reply  cached    uncached  compute saved
  --------------------------------------------------
  512       256     768     163,712           213x
  2,048     512   2,560   1,179,392           461x
  8,192   1,024   9,216   8,912,384           967x
  32,768  2,048  34,816  69,204,992          1988x

  So the trade is roughly 10x the memory for 200-2000x the compute,
  and the saving grows with context while the memory cost grows only
  linearly. That is why no serving stack ships without a KV cache —
  it is not a tuning option, it is what makes hosting viable.

  and at 128k context, how the cache compares to the weights:

  model        batch    weights  KV cache @128k  cache/weights
  --------------------------------------------------------------
  Llama-3-8B       1   15.0 GiB        16.0 GiB          1.07x
  Llama-3-8B       8   15.0 GiB       128.0 GiB          8.56x
  Llama-3-8B      32   15.0 GiB       512.0 GiB         34.23x
  Llama-3-70B      1  131.5 GiB        40.0 GiB          0.30x
  Llama-3-70B      8  131.5 GiB       320.0 GiB          2.43x
  Llama-3-70B     32  131.5 GiB      1280.0 GiB          9.73x

  GQA vs MHA cache reduction         4.0x

  >> At long context the KV cache is larger than the model. It scales with batch AND sequence, while the weights are fixed — so it, not the checkpoint, is what caps concurrent users.

4. Prefill vs decode
--------------------------------------------------------------------------
  toy model parameters               62.6M
  weight bytes (fp32)                0.23 GiB

  phase    tokens/pass  ms/pass  ms/token    tokens/s
  -----------------------------------------------------
  prefill          512  33.8788    0.0662  15112.7181
  decode             1   5.7932    5.7932    172.6159

  per-token cost, decode / prefill   87.6x
  Both passes read the same weights. Prefill amortizes that read over
  512 tokens; decode pays it for one.

  arithmetic intensity (FLOPs per byte of weights read):

  phase    tokens  FLOPs (2*N*P)  weight bytes  FLOP/byte
  ---------------------------------------------------------
  prefill     512         64.1 G      0.23 GiB   256.0000
  decode        1        0.125 G      0.23 GiB     0.5000
  Modern accelerators need ~100-300 FLOP/byte to saturate their ALUs.

  decode step with a 32-token prefix (KV traffic at batch 32: 0.016 GiB vs 0.23 GiB of weights):

  batch  ms/step  latency vs b=1  tokens/s  throughput vs b=1
  -------------------------------------------------------------
  1       4.3755           1.00x       229               1.0x
  2       4.6257           1.06x       432               1.9x
  4       4.9239           1.13x       812               3.6x
  8       6.1775           1.41x      1295               5.7x
  16      6.7945           1.55x      2355              10.3x
  32      8.3636           1.91x      3826              16.7x

  decode step with a 512-token prefix (KV traffic at batch 32: 0.250 GiB vs 0.23 GiB of weights):

  batch  ms/step  latency vs b=1  tokens/s  throughput vs b=1
  -------------------------------------------------------------
  1       5.8571           1.00x       171               1.0x
  2       7.2173           1.23x       277               1.6x
  4       9.7919           1.67x       409               2.4x
  8      15.4096           2.63x       519               3.0x
  16     23.0585           3.94x       694               4.1x
  32     40.9820           7.00x       781               4.6x

  throughput gain at batch 32, 32-tok prefix 16.7x
  throughput gain at batch 32, 512-tok prefix 4.6x

  >> With a short prefix, 32x the work costs far less than 32x the time: the weight read was the bottleneck and the extra sequences rode along free. With a long prefix the gain shrinks, because KV traffic scales with batch while weight traffic does not. That is the whole economics of serving.
